## 1. 为什么需要重新基线

早期方案把 System Optimizer 主要表达为“在现有 optimization 实验上增加系统参数搜索”。后续讨论明确了更完整的产品边界：系统首先需要成为操作系统配置的采集、管理、人工修改、验证、回滚和审计底座，通用调优与 workload 调优是建立在该底座上的两条不同闭环。

旧方案中的 Config Manifest、Profile、补偿式 apply、verify、rollback、simulated backend 和证据链仍有保留价值，但以下定义已经不完整或需要重新打开：

- 配置采集不是辅助探针，而是第一等功能。
- 用户手动修改、通用调优候选和 workload 调优候选应共用安全执行闭环。
- 通用调优与 workload 调优的观测、路由和评分方式不同。
- workload 的系统微指标用于下钻、解释和生成瓶颈假设，不直接决定整体优化分数。
- 优化任务必须有限并有显式停止条件；配置采集本身可以独立于优化任务存在。
- 旧决策 D0-08 的“缺省只由预算停止”需要重新评审，不能静默沿用或静默删除。
- 旧文档中的 cache mode 是测量环境的冷热缓存控制，不等同于未来对优化器中间结果的缓存和复用。

## 2. 已确认的产品边界

### 2.1 第一阶段形态

第一阶段是“离线或受控环境中的有限闭环调优”。

必须满足：

- 每次调优都是有开始、有限预算、停止原因和最终状态的任务。
- 不实现生产环境中的 always-on 自动改参 daemon。
- 不实现根据 workload 阶段实时切换系统配置的在线控制器。
- 真实系统修改仍受 preflight、snapshot、apply、verify、measure、rollback-or-explicit-keep 约束。
- 真实 local Linux 和远程后端的成熟度必须按实测如实标注，未验证时不得宣称可用。

### 2.2 共同配置底座

总体顺序为：

1. 发现并全量采集当前操作系统配置。
2. 保存配置的当前值、期望值、实际生效值、来源、所有权、作用域、合法域和证据。
3. 支持用户查看和手动修改配置。
4. 对任何修改先建立可恢复快照。
5. 将人工修改、通用调优和 workload 调优统一送入安全执行闭环。
6. 保存配置版本、应用结果、验证结果、回滚结果和审计轨迹。

配置采集、人工管理和调优任务属于同一产品，但生命周期不同：配置资产可以持续存在；单次优化任务必须有限结束。

### 2.3 暂不实施的过程优化

缓存和复用中间链路是后续“优化器过程优化”阶段，不在当前功能闭环范围内。当前只要求证据带有足够的环境、配置、workload、工具和版本身份，以便未来能够安全设计缓存键和失效规则。

当前不得：

- 因历史结果看起来相似而跳过真实采集或真实测量。
- 默认跨机器、跨内核、跨 workload 或跨阶段复用结果。
- 把工作负载冷热缓存控制与优化器证据缓存混为一谈。

## 3. 两条调优路径不是同一种算法

### 3.1 系统通用调优

通用调优在没有真实业务 workload 的情况下，使用受控、可重复的标准压力对组件进行测试。准确名称是“无业务载荷的标准压力调优”，不是字面上的空载调优。

主要特征：

- 压力方式、组件范围和实验协议相对固定。
- 按 CPU、内存与 NUMA、存储、网络以及后续可选加速器组织。
- 组件主指标负责评价本组件，其他组件指标主要作为退化门禁和解释证据。
- 各组件候选不能直接把局部最高分相加；组合配置必须经过混合压力重新实测。
- 输出是带适用环境、证据、风险和回滚信息的通用基础 Profile。

这里的“静态”是指目标、压力协议和搜索空间相对固定，不代表测量值不随时间变化。

### 3.2 workload 场景调优

workload 调优是观测驱动的动态下钻闭环：

1. workload manifest 声明业务目标、SLO、阶段和必要上下文。
2. 运行 workload，并同步采集业务指标和低开销系统指标。
3. 从业务退化或资源压力出发，路由到一个或多个候选组件。
4. 在候选组件内按需启动更细的微指标采集。
5. 在单个组件内部计算指标优先级，形成瓶颈假设。
6. 将假设映射到允许修改的配置候选。
7. 执行受控干预实验。
8. 回到 workload 业务指标、SLO 和稳定性验证是否真正改善。
9. 重新观测；瓶颈可能转移，因此重新下钻和分配预算。
10. 达到目标、收敛、耗尽预算、安全停止或用户取消后结束。

workload 用于定义场景和证明优化能力，不负责反向定义通用组件指标体系。

## 4. workload 的分层观测与下钻

### 4.1 低开销优先

动态指标采集必须控制观察者效应，按成本分层：

| 层级 | 内容 | 启用方式 | 目的 |
|---|---|---|---|
| L0 | 业务吞吐、延迟、完成时间、错误率、SLO | workload 期间持续或按协议采集 | 判断业务是否退化、最终是否改善 |
| L1 | 低开销资源压力和占用 | 持续或低频周期采集 | 初步路由到候选组件 |
| L2 | 组件微指标 | 下钻触发后限时采集 | 区分组件内部瓶颈假设 |
| L3 | 高开销 trace、profiling、详细事件 | 证据不足且明确授权后启用 | 深度定位，不能默认常开 |

每个指标必须记录采集成本等级、工具、时间窗口、采样频率、作用域、可用权限和是否发生 multiplexing 或数据丢失。未测量采集开销时，不能宣称“低开销”，只能标记为设计目标或未验证。

### 4.2 下钻层级

建议的逻辑层级是：

业务症状 → 资源域 → 组件压力 → 微指标 → 瓶颈假设 → 可控配置 → 干预实验 → 业务复验

观测到的相关性只允许生成假设，不允许直接写成根因。只有受控修改后业务结果按协议发生可重复变化，才能提高因果可信度。

### 4.3 组件不是封闭孤岛

指标优先级在单个组件内部计算，但诊断路由必须允许跨组件关系。例如 CPU 等待存储、内存回收产生存储 I/O、NUMA 同时影响 CPU 与内存、网络中断形成 CPU 热点。

因此诊断结果至少需要表达：

- primary component：本轮主要下钻组件。
- related components：可能共同参与或受影响的组件。
- competing hypotheses：尚未通过干预排除的竞争假设。

不能因为选择了 primary component 就静默丢弃其他有证据的组件。

## 5. 组件内二维指标优先级

二维优先级只在已经选定的单个组件内部使用，不进入整个系统的最终调优公式。

两个维度是：

1. 当前不利压力程度：指标当前值相对容量、SLO、安全阈值或同阶段正常范围的压力。
2. 不利变化程度：指标相对可比基准向坏方向变化的幅度。

| 当前不利压力 | 不利变化 | 组件内含义 |
|---|---|---|
| 高 | 大 | 正在恶化的高压热点，优先下钻 |
| 高 | 小 | 持续存在的稳定瓶颈，保持高优先级 |
| 低 | 大 | 新出现的潜在风险，验证持续性和阶段影响 |
| 低 | 小 | 当前证据弱，暂不分配高成本采集预算 |

该二维结果回答“组件内部先调查什么”，不回答“整个系统哪个候选最好”。

### 5.1 指标方向不能只考虑上升

每个指标必须声明语义方向，至少支持：

- maximize：越高越好，下降才是不利变化。
- minimize：越低越好，上升是不利变化。
- target：距离目标越远越差。
- range：只有越出允许区间才差。
- diagnostic only：只做解释，不计算优化优先级。

不得把所有上升都写成问题。例如吞吐和缓存命中率上升可能是改善；延迟、错误率、排队和重传上升通常是不利；CPU 利用率、内存占用和带宽需要结合作用域与压力指标解释。

### 5.2 相对变化不是唯一算法

正值且基线远离零时，可将方向感知的相对变化作为候选计算方式。基线接近零、允许负数、目标型或区间型指标不能直接套用同一比例，否则会放大噪声或产生无意义结果。

具体公式、近零判定、时间窗口和统计估计器尚未确认，不能提前写入实现。至少必须保留：

- 原始值和单位。
- 可比基准及其来源。
- 指标方向。
- 绝对变化和相对变化。
- 时间窗口、workload 阶段和作用域。
- 持续性、出现频率和测量不确定性。

### 5.3 高值必须有参照和作用域

“高”不能来自通用常数。参照可以是硬件容量、业务 SLO、安全界限、同 workload 同阶段基线或经过实测确认的正常分布。

必须支持 host、NUMA node、CPU core、device、queue、network interface、process/thread、cgroup、container 和 VM 等作用域。整机平均值不得冒充局部热点，例如总 CPU 利用率较低时仍可能存在单核饱和。

### 5.4 workload 阶段与持续性

初始化、加载、稳态、checkpoint 和收尾的指标分布可能天然不同。指标变化必须尽可能在相同 workload 阶段之间比较。

第一阶段阶段信息只用于保证比较公平，不自动产生阶段专用配置，也不在线切换 Profile。

瞬时尖峰、阶段切换和持续瓶颈必须区分。变化幅度大的指标至少还需要持续性或重复出现证据，才能提升下钻优先级。

## 6. 评分与优先级必须分离

System Optimizer 至少存在四类不同结果，不能混成一个数：

| 类型 | 作用 | 是否决定最终候选成功 |
|---|---|---|
| 组件内微指标优先级 | 组件内部下钻顺序 | 否 |
| 瓶颈假设可信度 | 决定优先验证哪条假设 | 否 |
| workload 候选业务收益 | 判断业务目标是否改善 | 是 |
| 安全、稳定性和证据充分性 | 候选晋级和发布门禁 | 是 |

候选必须先通过正确性、安全、SLO、证据完整性和稳定性门禁，再讨论业务收益。违反硬门禁的候选是 infeasible，不允许靠其他指标补分。

场景调优的最终结果由业务目标决定。系统微指标用于路由、解释、约束或成本核算，除非 workload 合同明确将某项系统资源成本声明为业务目标，否则不得自动加入整体业务得分。

通用调优优先保存 CPU、内存与 NUMA、存储、网络、稳定性和跨组件退化等分项结果。第一阶段不假设存在跨所有 workload 通用的固定总权重。

同一候选至少保留三种比较：

- 相对冻结原始基线：用于最终报告。
- 相对当前最佳候选：用于搜索替换决策。
- 场景调优相对通用 Profile：用于说明场景调优的增量价值。

## 7. 不能遗漏的错误防护

以下规则必须进入后续规范和验收：

1. 不把高占用自动等价为瓶颈。
2. 不把所有指标上升自动等价为退化。
3. 不用整机平均值掩盖核、NUMA、设备、队列或进程级热点。
4. 不跨 workload 阶段直接比较变化比例。
5. 不把相关性、同时变化或时间相关直接写成因果根因。
6. 不把组件内部二维优先级加入整体业务得分。
7. 不把一个组件的局部最优直接与其他组件局部最优拼接后宣称全局最优。
8. 不让违反正确性、安全或 SLO 的候选通过加权补偿获胜。
9. 关键业务目标或硬门禁指标缺失时不评分、不发布；不得静默重分配剩余权重。
10. 不把论文数字、fixture、synthetic adapter 输出或推测填成本项目真实测量。
11. 不凭相同指标名判断语义等价；字段映射必须有来源并经过抽样或实测验证。
12. 不宣称某个采集器低开销，除非在目标环境测过观察者开销。
13. 不把本次预算内 best observed 写成已证明的全局最优。
14. 不跨硬件、内核、workload、数据集、工具版本和评分协议默认比较分数。
15. 不在任务崩溃后盲目重试 apply；恢复前必须重新采集并对账实际状态。
16. 不允许同一目标上的两个写任务、人工修改与调优任务无协调并发。

## 8. 停止、并发和恢复的架构要求

停止必须分层：

- 单次测量：错误、超时、安全违规、关键数据不可用。
- 单个候选：证据已经足以接受或拒绝。
- 单个组件：搜索空间结束，或在已确认统计规则下没有有意义提升。
- 整个任务：达到目标、全局收敛、预算耗尽、无法安全恢复或用户取消。

具体最小有效提升、置信水平、重复次数和无改进轮次仍未校准，不能写通用默认值。旧 D0-08 因产品讨论变化进入“重新打开”，不是已经被新数值替代。

并发建议采用同一目标单写者租约、只读采集可并发，但租约、人工修改优先级和外部 daemon 冲突的正式协议仍待确认。

崩溃恢复必须先将实际配置与任务快照、期望状态和审计事件对账，再决定继续、回滚或 needs-attention。

## 9. 配置所有权和动态合法域仍待确认

配置状态至少需要区分：当前采集值、用户期望值、实际生效值、持久化值、优化器建议值和外部写入值。

用户手动修改还需要明确是：

- 单次修改。
- 固定配置，优化器不可触碰。
- 新的调优基线。
- 保存为可复用 Profile。

搜索合法域至少需要区分：声明或理论范围、目标机器实际支持范围、本次任务获准范围。后者必须是前两者经过运行时验证后的安全子集。

这些语义尚未确认，旧实现中的单一 pinned 状态和静态 ValueDomain 不能直接视为最终合同。

## 10. 当前实现与历史验证事实

迁移时的工作树事实：

- 当前分支为 system-optimizer，跟踪 origin/main。
- M0 计划测试锚点的如实计数是 36，计数键为旧方案中“计划：tests/test_system_opt_...”条目；此前 37 的原始文本匹配把目录树中的 tests/test_system_opt_*.py 模式也计入，不能继续报告为 37。
- M0 的 187 项全量测试在共享 pytest 临时根和多 agent 并发场景出现过失败/ERROR；使用独立 basetemp 复跑后为 187/187。该证据只能支持“环境争用与真实时间分辨率缺陷未区分”，不能定性为既有 flaky test，时钟 tick 假设仍是未验证推断。
- Config Manifest、Profile、安全执行器、simulated/local/SSH backend 的部分 M1 Python 代码和 33 个相关测试已经存在于未提交工作树。
- 迁移开始时，根 README 和模块 README 仍声称“没有 Python 实现”，属于当时的文档状态滞后；迁移后入口已经更正，但历史副本保留原文。
- 此前使用独立 basetemp 的全量测试记录为 220/220 通过；本次文档迁移没有据此宣称真实 Linux/CVM 能力已经验证，也不代表后续修改后仍自动全绿。
- 已报告但尚未修复的 A 级实现问题：ConfigItem.preconditions 已声明但 SafetyController preflight 未执行；当前 apply 项在失败、超时或 unknown 时可能未进入补偿列表，存在部分施加状态逃逸回滚的风险。
- 在架构重新基线并确认前，不继续扩展 M1 实现，也不把现有类型当成最终稳定合同。

## 11. 文档迁移原则

本次迁移必须无损、可追溯：

- 旧主方案进入 legacy，不删除，不伪装为当前合同。
- 原指标盘点作为 source inventory 保留，不擅自筛字段、合并同名指标或修改计数口径。
- 新目录的 README 是唯一当前入口。
- 每份规范标明状态、适用阶段、已确认项、待确认项、事实与推断。
- 决策变化记录“原决定、变化原因、新状态”，不静默改写历史。
- 规范使用 MUST、SHOULD、MAY 时必须给出适用范围；草案建议不得使用已实现口吻。
- 代码、测试、文档状态必须分别报告，不能用其中一个替代另一个。

## 12. 新文档必须覆盖的主题

新框架至少包含：

- 产品范围、边界、术语和决策日志。
- 配置采集、人工修改、Profile 和配置所有权。
- 通用标准压力调优架构。
- workload 动态观测、低开销采集和下钻架构。
- 指标字段、方向、作用域、阶段、成本和语义验证协议。
- 组件内优先级、瓶颈假设和整体候选评分的分离。
- 安全 apply/verify/rollback、并发租约、崩溃恢复和多节点边界。
- 有限任务状态机、分阶段晋级和停止条件。
- 证据、结果定性、验收标准和实施路线图。
- 后续过程优化，包括缓存和中间结果复用的明确 backlog。

## 13. 尚未确认、不得写入实现的事项

- 跨组件诊断路由的具体规则或算法。
- 二维优先级的具体归一化公式和高/低阈值。
- 近零基线如何切换到绝对变化或分布偏离。
- workload 阶段是 manifest 显式标注、自动识别还是组合方式。
- 各指标采集成本等级在真实目标上的实测结果。
